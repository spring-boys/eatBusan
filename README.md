## 1. 기획 요약

부산광역시 모범음식점 데이터를 기반으로 **지역구별 음식점 탐색**, **커뮤니티 후기 공유**, **QR 초대 코드 기반 방 입장**, **WebSocket 실시간 참여자 갱신**을 제공한다.

### 사용자 문제 정의

| 구분 | 내용 |
|------|------|
| 사용자 | 부산광역시에서 검증된 모범음식점을 찾고 싶은 사람 |
| 문제 | 모범음식점만 보기 좋게 정리된 서비스와 관련 커뮤니티가 부족하다 |
| 해결 | 지역구별 모범음식점 탐색, 후기 공유, 함께 고르기 경험을 제공한다 |
| 성공 기준 | 음식점 조회, 게시글 작성, QR 방 초대, 마이페이지 관리를 막힘없이 수행 (MVP 기준) |

### 주요 사용자 시나리오

1. 서비스에 접속해 **지역구별 부산 모범음식점**을 탐색한다.
2. 음식점 **상세 정보**와 커뮤니티 **후기**를 확인한다.
3. 로그인 사용자가 **게시글, 좋아요, 댓글**로 의견을 공유한다.
4. 방을 만들고 **QR 초대 코드**를 공유하면 초대받은 사용자가 링크로 입장한다.
5. 방 참여자는 **WebSocket**으로 실시간 참여자 상태를 확인한다.
6. **마이페이지**에서 프로필과 내 활동을 관리한다.

## 2. MVP 기능 정의

| 우선순위 | 기능명 | 대상 사용자 | 설명 | 완료 기준 |
|----------|--------|-------------|------|-----------|
| **P0** | 로그인 / 회원가입 | 비회원 | 이메일/비밀번호 또는 OAuth 기반 인증 | 로그인 성공 시 인증 토큰 발급 |
| **P0** | 지역구별 모범음식점 조회 | 전체 | 부산 16개 구/군 기준 목록/상세 조회 | 구/군 필터, 검색, 상세 조회 가능 |
| **P0** | 음식점 관리 | 관리자 | 공공데이터 기반 모범음식점 등록/수정/삭제 | API 및 화면 제공 |
| **P0** | 게시글 관리 | 회원 | 커뮤니티 게시글 작성/조회/수정/삭제 | 목록, 상세, 작성, 수정, 삭제 가능 |
| P1 | 게시글 좋아요 및 댓글 | 회원 | 게시글 좋아요·취소, 댓글 작성/삭제 (대댓글 없음) | 중복 좋아요 방지, 댓글 목록 표시 |
| P1 | QR 초대 방 관리 | 회원 | 방 생성 후 QR 초대 링크 공유, 초대 코드로 입장 | QR 스캔 또는 링크 접속 후 입장 가능 |
| P1 | 방 참여 상태 실시간 확인 | 회원 | 방 입장/퇴장/대기 상태를 WebSocket으로 갱신 | 참여자 목록이 실시간 변경 |
| P1 | 마이페이지 관리 | 회원 | 프로필 수정, 내 게시글/댓글/좋아요/찜/방 목록 조회 | 내 정보 수정과 내 활동 목록 조회 가능 |

## 3. 요구사항 설계

### 기능 요구사항

| ID | 요구사항 | 우선순위 | 비고 |
|----|----------|----------|------|
| FR-01 | 사용자는 회원가입 및 로그인을 할 수 있다 | P0 | JWT 또는 세션 방식 확정 필요 |
| FR-02 | 사용자는 부산 구/군별 모범음식점 목록을 조회할 수 있다 | P0 | district 필터, 검색, 페이징 |
| FR-03 | 사용자는 모범음식점 상세 정보를 조회할 수 있다 | P0 | 주소, 전화번호, 메뉴, 리뷰, 북마크 |
| FR-04 | 관리자는 음식점 정보를 등록/수정/삭제할 수 있다 | P0 | 소프트 삭제 기본 |
| FR-05 | 회원은 게시글을 작성/조회/수정/삭제할 수 있다 | P0 | 작성자 또는 관리자만 수정/삭제 |
| FR-06 | 회원은 게시글에 좋아요를 누르거나 취소할 수 있다 | P1 | 사용자별 중복 좋아요 방지 |
| FR-07 | 회원은 게시글에 댓글을 작성/삭제할 수 있다 | P1 | 대댓글은 범위 제외 |
| FR-08 | 회원은 방을 생성하고 QR 초대 코드를 공유할 수 있다 | P1 | PickEat room 구조 참고 |
| FR-09 | 초대받은 사용자는 QR 링크 또는 초대 코드로 방에 입장할 수 있다 | P1 | 비로그인 상태면 로그인 후 복귀 |
| FR-10 | 방 참여자는 WebSocket으로 입장/퇴장 이벤트를 실시간 확인할 수 있다 | P1 | `/topic/rooms/{roomCode}` 구독 고려 |
| FR-11 | 사용자는 마이페이지에서 프로필과 내 활동을 조회/수정할 수 있다 | P1 | 내 글, 댓글, 좋아요, 찜, 참여 방 |

### 비기능 요구사항

| ID | 항목 | 요구사항 |
|----|------|----------|
| NFR-01 | 사용성 | 모바일 우선 화면으로 핵심 액션이 2~3탭 안에 도달해야 한다 |
| NFR-02 | 성능 | 목록 조회는 페이징을 기본으로 하고 구/군, 카테고리, 삭제 여부 인덱스를 사용한다 |
| NFR-03 | 보안 | 인증 필요 API는 로그인 사용자만 접근 가능해야 하며 작성자 권한을 검증한다 |
| NFR-04 | 실시간성 | QR 방 입장/퇴장 이벤트는 WebSocket으로 1초 내 반영을 목표로 한다 |
| NFR-05 | 데이터 품질 | 공공데이터의 원본 식별자와 기준일을 저장해 중복 적재를 방지한다 |

## 6. DB 설계

- DDL 파일: `src/main/resources/db/schema.sql`
- 상세 문서: `DB_SCHEMA_DESC.md`

**핵심 테이블**

```
district → excellent_place → place_menu, place_image
users → post → post_comment, post_like
       → place_bookmark, place_review
```

**추가 검토 테이블 (QR 방 기능)**

```
room, room_user, room_invite
```

## 7. API 엔드포인트 초안

| Method | Endpoint | 설명 | 인증 |
|--------|----------|------|------|
| POST | `/api/v1/auth/signup` | 회원가입 | N |
| POST | `/api/v1/auth/login` | 로그인 | N |
| GET | `/api/v1/places` | 음식점 목록 | N |
| POST | `/api/v1/places` | 음식점 등록 | Y/Admin |
| GET | `/api/v1/posts` | 게시글 목록 | N |
| POST | `/api/v1/posts` | 게시글 작성 | Y |
| POST | `/api/v1/posts/{postId}/likes` | 게시글 좋아요 | Y |
| POST | `/api/v1/posts/{postId}/comments` | 댓글 작성 | Y |
| POST | `/api/v1/rooms` | 방 생성 | Y |
| POST | `/api/v1/rooms/{roomId}/invite-code` | QR 초대 코드 생성 | Y |
| POST | `/api/v1/rooms/join` | 초대 코드로 방 입장 | Y |
| WS | `/ws/rooms`, `/topic/rooms/{roomCode}` | 방 참여자 실시간 갱신 | Y |
| GET | `/api/v1/me` | 내 정보 조회 | Y |
| PATCH | `/api/v1/me` | 내 정보 수정 | Y |

## 10. 결정 사항 / 다음 액션

### 결정된 사항

- 대댓글은 MVP에서 **제외**한다.
- QR 초대 코드는 PickEat의 방 구조를 참고하되, **코드 기반 입장 + WebSocket 갱신** 추가.
- 유스케이스 다이어그램은 Figma가 아니라 **PlantUML PNG** 로 관리한다.

### 논의 필요 사항

- [ ] 로그인 방식: 로컬/JWT만 할지, OAuth까지 포함할지 확정
- [ ] 음식점 관리 권한: 관리자 전용 vs 로그인 사용자 전체 공개 확정
- [ ] QR 초대 코드 만료 시간과 재사용 가능 여부 확정

- [ ] DB 설계에 `room`, `room_user`, `room_invite` 반영
- [ ] 음식점 상세 화면 와이어프레임 추가
